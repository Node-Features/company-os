Phase 3 Slice 2 — Governance `REQUIRE_APPROVAL` path + the Approval domain (2026-08-23). The roadmap's own suggested trigger (non-owner `CANCEL_WORKFLOW`) was unavailable — Slice 1 made that a `DENY`, and Governance must stay deterministic for the identical request shape. Chosen trigger: cancelling an already-`READY` (dispatched) Workflow requires human approval; a `PLANNED` cancel stays automatic (`internal/application/workflow_cancel.go`'s `cancelAutonomyRequirement`). `governance.Request` gained two fields: `AdditionalAutonomyRequirement *policy.AutonomyLevel`, composed with the matched policy Rule's autonomy via most-restrictive-wins — the first real implementation of governance.md step 5's composition rule, which had only ever had one autonomy source (the Rule table) to compose before this; and `ApprovalEvidence`, which unlocks `ALLOW` only when its `ProposalDigest` exactly matches the request's (governance.md step 7, literal wording).

Designing the resumption mechanism surfaced two more unexercised Phase 1 gaps in the same code, both now fixed: `evaluateGovernance`'s `REQUIRE_APPROVAL` branch never set `command.PendingCommand.GovernedPayload` (`NOT NULL` in the schema — the insert would have failed the first time this path actually ran, same class of bug as the `SaveGovernanceDecision` gap above); and there was no resolution/resume mechanism at all — `CommitTransition`'s `closePendingCommand`/`consumeApproval` parameters were already correctly implemented in the repository, just never called with non-nil values by anything.

Key design decision, validated against `kernel/workflow/digest.go`: `ProposalDigest` hashes the *entire* `WorkflowCommandEnvelope` (including `DeclaredTime`, `CommandID`, everything), so a freshly-reconstructed command at resume time could never reproduce a matching digest. The resolution: persist the original envelope verbatim in `GovernedPayload` at `REQUIRE_APPROVAL` time, and replay it byte-for-byte (deserialized, unmutated) through the same `kernelwf.ValidateCancelProposal` at resume time (`internal/application/approval_resolve.go`'s `resumeCancelWorkflow`). When nothing about the Workflow changed in between, the recomputed digest matches automatically (pure function of unchanged inputs); when it did change, Kernel's existing version/state checks reject before Governance is even consulted — no special-case digest logic needed, just correct reuse of existing machinery.

New `ports.PendingCommandRepository.ResolveApproval` (Postgres implementation in `pending_repo.go`) performs the human decision as one compare-and-swap on `approvals.status='PENDING'` — zero rows affected (already decided, or never existed) returns `ports.ErrConflict`, which is the sole concurrency guard against double-resolution/double-resumption; no separate lock needed. New fixture `fixtures.ApproverPrincipal()` (Kind `HUMAN`, `PrincipalID` `...-4000-8000-...006`) is distinct from the Service `TriggerPrincipal` that always requests, making `docs/domain/approval.md`'s "only a human, not the requester, may approve" real rather than vacuous — enforced by construction (the two Principals can never collide given how `CancelWorkflowRequest`/`ResolveApprovalRequest` are wired this slice) rather than a runtime check guarding an unreachable branch, matching this codebase's "don't validate what can't happen" convention.

New HTTP endpoint `POST /v1/approvals/{approvalId}/decide` (`internal/adapters/httpapi/approvals.go`), registered in `main.go`; `workflowCommandResponse` gained `approvalId`. `web` gained `resolveApproval` in `companyd-client.ts`, a proxy route at `apps/web/app/api/approvals/[id]/decide/route.ts`, and Approve/Reject buttons in `WorkflowTrigger.tsx` shown when a Cancel returns `APPROVAL_REQUIRED` — the first Phase 3 slice needing an actual new UI affordance (Slice 1's `DENY` was already fully representable by the existing generic error display).

## Decided implementation choices

All four are now settled by the approved `docs/adr/ADR-0004-first-slice-technology-stack.md` (2026-08-21):

- Runtime implementation: internal, in Go, inside `companyd`.
- Persistence adapter: Supabase/Postgres, state-plus-outbox (not event sourcing).
- Notification recovery: Supabase Realtime (`LISTEN`/`NOTIFY`) direct path plus a Runtime polling sweep fallback; no message broker.
- First `CapabilityDefinition`: a minimal `IntelligenceCapability` for short bounded text generation, one `ModelProfile`/`ProviderAdapter`.

`companyd` hosting is decided: local development runs `companyd` via `air` (hot-reload) against Supabase; production runs `companyd` on a DigitalOcean VPS supervised by systemd, satisfying `daemon.md`'s external-supervision expectation. `ADR-0004`'s four sub-questions were left open at approval time as implementation detail, not a blocker — the Phase 1 implementation has since answered them in code (the ADR text itself is unchanged, per its immutability rule):

- LLM provider/model: not one fixed choice — `internal/adapters/intelligence/fallback` composes Gemini (`gemini-2.5-flash`), OpenAI (`gpt-5-nano`), and Anthropic (`claude-haiku-4-5`) behind one `ProviderAdapter`, trying them in priority order and skipping one that just rate-limited or went down (60s cooldown) rather than failing the dispatch.
- Transport: plain REST/JSON on `companyd`'s `net/http` mux (Go 1.22+ method+pattern routing); `web`'s Next.js Route Handlers proxy to it via `fetch`.
- Supabase RLS: enabled with zero policies on every table (default-deny to the `anon`/`authenticated` PostgREST roles `web`'s publishable key uses); `companyd`'s pooled `DATABASE_URL` role is the trusted backend and bypasses RLS. Organization isolation is enforced at the Application/Kernel layer, not the DB layer, this slice.
- Retry policy: 3 attempts (1 + 2 retries), exponential backoff base 2s capped at 30s, full jitter — fields on the `bounded-text-generation` `CapabilityDefinition` fixture, not hardcoded in Runtime.
