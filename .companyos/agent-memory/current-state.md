Authorized-Principal enforcement checks the requesting Principal against the Workflow's `InitiatingPrincipalID` (rejecting a mismatch with `PRINCIPAL_NOT_AUTHORIZED`) at the Kernel layer, not via a Governance role rule — Governance's `workflow.*` permit rule is action-scoped, not resource-instance-scoped, so it can't express "only the Workflow's own initiator." `ports.AuthoritativeStateRepository.CommitTransition` gained a `closeOutstandingIntent bool` parameter: cancelling a `READY` Workflow atomically marks any still-`PENDING` `execution_intents` row `CLOSED` in the same transaction as the Workflow state write, so Runtime's due-intent claim query never picks it up — verified live against the real database (a Workflow cancelled immediately after `START_WORKFLOW` never appears in Runtime's dispatch log). Realtime activity layer (Slice 8, 2026-08-22) made `internal/ports.Publisher` and the previously-unread `event_outbox` table real for the first time: `internal/ports.OutboxRepository` (new) + `internal/adapters/notify/realtime.Sweeper` (new, ~1s poll) load not-yet-published events and drive `internal/adapters/persistence/supabase.RealtimePublisher` (new), which broadcasts a minimal hint over Supabase Realtime via the `realtime.send()` SQL function called over the existing `DATABASE_URL` pool — not an HTTP call to Supabase's REST API. This was a mid-implementation design change from the original plan (an HTTP call authenticated with `SUPABASE_SERVICE_ROLE_KEY`): the project owner redirected to reuse `DATABASE_URL` instead, which turned out to remove the new-credential requirement entirely (`SUPABASE_SERVICE_ROLE_KEY` remains declared in `.env.example`/`.env` but is unused by this feature). Broadcast (not `postgres_changes`) was chosen specifically because it needs no RLS SELECT policy and no schema migration — it never touches a table's replication stream, so the zero-RLS-policy posture `ROADMAP.md` Phase 9 Slice 4 still gates is untouched. `web`'s `WorkflowTrigger` subscribes directly to a per-Workflow `workflow:<id>` topic with the existing publishable-key browser client, treating a broadcast as a hint (refetches `GET /v1/workflows/{id}` rather than trusting the payload), with a ~15s reconciliation poll as a fallback for a dropped socket. Verified live: subscribing with only the publishable key and triggering `START_WORKFLOW` through `companyd` delivered the broadcast in under a second; the integration test `TestRealtimePublisher_Publish_WorkflowEventSucceeds` (`internal/adapters/persistence/supabase`) confirms the `DATABASE_URL` role has the required `EXECUTE` grant on `realtime.send()`.

## Decided implementation choices

All four are now settled by the approved `docs/adr/ADR-0004-first-slice-technology-stack.md` (2026-08-21):

- Runtime implementation: internal, in Go, inside `companyd`.
- Persistence adapter: Supabase/Postgres, state-plus-outbox (not event sourcing).
- Notification recovery: Supabase Realtime (`LISTEN`/`NOTIFY`) direct path plus a Runtime polling sweep fallback; no message broker.
- First `CapabilityDefinition`: a minimal `IntelligenceCapability` for short bounded text generation, one `ModelProfile`/`ProviderAdapter`.

`companyd` hosting is decided: local development runs `companyd` via `air` (hot-reload) against Supabase; production runs `companyd` on a DigitalOcean VPS supervised by systemd, satisfying `daemon.md`'s external-supervision expectation. `ADR-0004`'s four sub-questions were left open at approval time as implementation detail, not a blocker — the Phase 1 implementation has since answered them in code (the ADR text itself is unchanged, per its immutability rule):

- LLM provider/model: not one fixed choice — `internal/adapters/intelligence/fallback` composes Gemini (`gemini-2.5-flash`), OpenAI (`gpt-5-nano`), and Anthropic (`claude-haiku-4-5`) behind one `ProviderAdapter`, trying them in priority order and skipping one that just rate-limited or went down (60s cooldown) rather than failing the dispatch.
- Transport: plain REST/JSON on `companyd`'s `net/http` mux (Go 1.22+ method+pattern routing); `web`'s Next.js Route Handlers proxy to it via `fetch`.
- Supabase RLS: enabled with zero policies on every table (default-deny to the `anon`/`authenticated` PostgREST roles `web`'s publishable key uses); `companyd`'s pooled `DATABASE_URL` role is the trusted backend and bypasses RLS. Organization isolation is enforced at the Application/Kernel layer, not the DB layer, this slice.
- Retry policy: 3 attempts (1 + 2 retries), exponential backoff base 2s capped at 30s, full jitter — fields on the `bounded-text-generation` `CapabilityDefinition` fixture, not hardcoded in Runtime.
