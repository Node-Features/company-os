Grounded in the [Application layer's first vertical slice](docs/architecture/application.md#first-vertical-slice) and the [Workflow first-slice lifecycle](docs/domain/workflow.md#first-slice-lifecycle). `ADR-0004` answers this phase's three long-standing open questions (Runtime, persistence adapter, first CapabilityDefinition) and was approved 2026-08-21.

All 9 slices are complete (Slices 6 and 8 both landed 2026-08-22): `CREATE_WORKFLOW → START_WORKFLOW → Runtime dispatch → ACCEPT/REJECT/CANCEL_WORKFLOW` works end to end against the real database and a real provider call, triggered from `web`, with live push updates replacing polling. Phase 1 is complete. The slices below are ordered so each one is independently buildable and testable — no slice depends on a later one.

Its four sub-questions remain open as implementation detail, not a blocker: first LLM provider, Next.js↔`companyd` transport, Supabase RLS design, first Retry policy defaults.

- [x] **Slice 3 — `CREATE_WORKFLOW`.** `internal/kernel/workflow` (proposal + final decision) + `internal/governance` (default-deny policy) + `internal/application.CreateWorkflow`. Covered by unit and integration tests.
- [x] **Slice 4 — `START_WORKFLOW` + Runtime.** `internal/runtime.Runtime` claims and dispatches via `internal/adapters/intelligence/fallback`, which tries Gemini/OpenAI/Anthropic in priority order and skips a provider that just rate-limited or went down (cooldown-based), rather than one fixed `ProviderAdapter`.

- [x] **Slice 6 — `CANCEL_WORKFLOW`.** `PLANNED` or `READY` → `CANCELLED`, authorized-Principal only (the Workflow's `InitiatingPrincipalID`; enforced in `internal/kernel/workflow.ValidateCancelProposal`, rejected with `PRINCIPAL_NOT_AUTHORIZED` otherwise). Cancelling a `READY` Workflow atomically closes its outstanding, still-`PENDING` `ExecutionIntent` in the same transaction as the state write (`ports.AuthoritativeStateRepository.CommitTransition`'s new `closeOutstandingIntent` parameter) so Runtime never dispatches it — verified live: a Workflow cancelled immediately after `START_WORKFLOW` never appears in Runtime's dispatch log. Does not assume an already-claimed in-flight attempt stopped immediately, per `execution.md`'s invariants. Exposed through `companyd` (`POST /v1/workflows/{id}/cancel`) and `web` (a Cancel button in `WorkflowTrigger`).
- [x] **Slice 7 — Expose it through `web`.** `internal/adapters/httpapi/workflows.go` (`POST /v1/workflows`, `.../start`, `.../results/{accept,reject}`, `GET /v1/workflows/{id}`) plus a Next.js trigger page (`components/WorkflowTrigger.tsx`) that creates, starts, and polls a Workflow to a terminal state — `web` calls `companyd` for this, never writes Supabase directly.
- [x] **Slice 8 — Realtime activity layer.** `WorkflowTrigger`'s 2-second poll is replaced with a push update: `internal/ports.OutboxRepository` (new) plus `internal/adapters/notify/realtime.Sweeper` (new) finally read `event_outbox` — nothing did before this slice — and drive `internal/adapters/persistence/supabase.RealtimePublisher` (new), which broadcasts a minimal per-event hint (`eventId`/`eventType`/`workflowId`/`subjectVersion`/`occurredAt`, not full Workflow state) over Supabase Realtime via the `realtime.send()` SQL function, called over the same `DATABASE_URL` pool every other repository already uses — not an HTTP call to Supabase's REST API, so no new credential (`SUPABASE_SERVICE_ROLE_KEY`) was needed after all, superseding this slice's original plan to use one. `web`'s `WorkflowTrigger` subscribes directly to a per-Workflow `workflow:<id>` broadcast channel with the existing publishable-key browser client (`lib/supabase/client.ts`), refetching `GET /v1/workflows/{id}` on receipt rather than trusting the broadcast payload as authoritative, plus a slow ~15s reconciliation poll as a safety net for a dropped socket — verified live: subscribing with only the publishable key (zero RLS policies, by design — Broadcast doesn't need any, unlike `postgres_changes`) and triggering `START_WORKFLOW` through `companyd` delivered the broadcast in under a second, and the Workflow reached `COMPLETED` normally. Scope note: one Workflow's live status (extends Slice 7 directly); a company-wide activity feed spanning multiple Workflows/departments is broader scope deferred to Phase 4+.

A direct DB inspection following this slice found a separate, pre-existing Phase 1 bug in the same code path: `evaluateGovernance`'s `ALLOW` branch never called `SaveGovernanceDecision`, so every governed command that succeeded (`workflow.create`/`.start`/`.result.accept`/`.result.reject`/`.cancel`) left `execution_intents.governance_decision_id` referencing a `governance_decisions` row that was never written — 100% of `execution_intents` in the live DB were orphaned this way, and `REQUIRE_APPROVAL`'s `CreatePendingApproval` would have failed its FK insert the first time it actually ran. Fixed by persisting the decision once, unconditionally, for every outcome, before branching — `governance.md`: "Policy, authority, approval, and decision records are persisted before dependent execution continues." Added `ports.AuthoritativeStateRepository.GovernanceDecisionExists` and `TestIntegration_CreateWorkflow_PersistsGovernanceDecision` to prove it against the real database; re-verified live afterward that `workflow.create`/`.start`/`.result.accept`/`.result.reject`/`.cancel` `ALLOW` decisions are now all present in `governance_decisions`.
- [x] **Slice 2 — Governance `REQUIRE_APPROVAL` path + the Approval domain (2026-08-23).** The roadmap's own suggested trigger (non-owner `CANCEL_WORKFLOW`) was no longer available — Slice 1 made that a `DENY`, and Governance must stay deterministic. Chosen trigger instead: cancelling an already-`READY` (dispatched) Workflow requires human approval; cancelling a `PLANNED` one stays automatic (`application.cancelAutonomyRequirement`). `governance.Request` gained `AdditionalAutonomyRequirement *policy.AutonomyLevel` (composed with the matched Rule's autonomy via most-restrictive-wins, `governance.md` step 5 — the first real implementation of that composition step) and `ApprovalEvidence` (governance.md step 7: `REQUIRE_APPROVAL` unlocks to `ALLOW` only when the evidence's `ProposalDigest` exactly matches the request's). New `ports.PendingCommandRepository.ResolveApproval` does the human decision as one compare-and-swap on `approvals.status='PENDING'` (0 rows affected → `ErrConflict`, preventing double-resolution without a separate lock). Verified against the real database (`internal/application/integration_test.go`): READY-cancel → `APPROVAL_REQUIRED` with an `ApprovalID`, Workflow untouched; approve → resumes and completes, `CANCELLED`; reject → Workflow stays `READY`; double-resolution → `CONFLICT`; PLANNED-cancel unaffected (still immediate). One test-hygiene fix along the way: tests that deliberately leave a Workflow `READY` with its `ExecutionIntent` still `PENDING` were polluting unrelated tests' organization-wide `ClaimDueIntents` claims across dev runs — `startedReadyWorkflow`'s `t.Cleanup` now drains it regardless of outcome.
