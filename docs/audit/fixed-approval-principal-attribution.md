## What was implemented

Two related fixes, matching the gap doc's two-part problem exactly.

**1. Approval decisions now attributed to the real caller.** `application.ResolveApprovalRequest` gained `DecidingPrincipal principal.Principal` ([request.go](../../apps/companyd/internal/application/request.go)). `httpapi.ResolveApprovalHandler` ([approvals.go](../../apps/companyd/internal/adapters/httpapi/approvals.go)) reads it from `PrincipalFromContext` and threads it through; `Application.ResolveApproval` ([approval_resolve.go](../../apps/companyd/internal/application/approval_resolve.go)) passes it straight to `a.Pending.ResolveApproval` instead of hardcoding `a.Fixtures.ApproverPrincipal()`. The port's structural self-approval/human-decider checks (`ports.ErrSelfApproval`/`ErrNonHumanDecider`, [`fixed-authority-model-formalization.md`](fixed-authority-model-formalization.md)) were already real — they just had nothing but a fixture to check before. Now they check the actual caller.

**2. Workflow commands now attributed to the real caller.** `CreateWorkflowRequest`/`StartWorkflowRequest`/`CancelWorkflowRequest` all gained `RequestingPrincipalID uuid.UUID`. `httpapi.CreateWorkflowHandler`/`StartWorkflowHandler`/`CancelWorkflowHandler` ([workflows.go](../../apps/companyd/internal/adapters/httpapi/workflows.go)) all now call the existing `requirePrincipal` helper (already used by every Research/M&E/Objective/Knowledge handler, [research.go](../../apps/companyd/internal/adapters/httpapi/research.go)) and pass the result through. `workflow_create.go`/`workflow_start.go`/`workflow_cancel.go` all read `req.RequestingPrincipalID` instead of `reg.TriggerPrincipal().PrincipalID`.

**Found during implementation, not in the gap doc's original file list**: `workflow_create.go` had to change too. `CancelWorkflow`'s ownership check compares the real caller against the Workflow's `InitiatingPrincipalID`, which `CreateWorkflow` sets from its own `RequestingPrincipalID` ([workflow_create.go:71](../../apps/companyd/internal/application/workflow_create.go#L71)). Leaving `CreateWorkflow` on the fixture while fixing `CancelWorkflow` alone would have meant `InitiatingPrincipalID` was permanently the fixture's ID, so a real caller could never satisfy the "only the initiator may cancel" check on a Workflow they legitimately created — the fix would have shipped a working compile and a broken feature. Caught by tracing the ownership check's data dependency before running tests, not by a test failure.

**Deliberately not changed**: `AuthorizeDispatch` ([workflow_start.go:89-107](../../apps/companyd/internal/application/workflow_start.go#L89-L107)) still uses `reg.TriggerPrincipal().PrincipalID`. It's Runtime's dispatch-time governance re-check, triggered by the poll loop, not an HTTP request — there is no authenticated caller to attribute it to. Documented in a new comment on the function rather than silently left as-is, so a future reader doesn't mistake it for a missed case.

**Design question the gap doc left open, left open here too**: "should any authenticated human decide any approval, or does this need a role/authority check first?" Implemented the minimal, already-structurally-supported answer — any authenticated human may decide, except the requester (the existing self-approval check) — per the milestone's own "no new features" constraint. A role/authority concept doesn't exist in this codebase yet and wasn't invented to answer this.

## Tests

Per the gap doc's own requirements, plus what was needed to keep ~30 pre-existing call sites (which previously relied on the removed fixture-substitution) meaningful rather than just compiling:

- `TestIntegration_CancelWorkflow_NonInitiatorDenied` — **rewritten**, not just patched: previously the Workflow's `InitiatingPrincipalID` was fabricated (`uuid.New()`) but the *requester* was implicitly always the fixture, so this could only prove "the fixture != a fabricated ID." Now both are explicit, distinct, real (non-fixture) `uuid.New()` values (`initiator` / `nonInitiatingRequester`) flowing through `RequestingPrincipalID` for real — proving two genuinely different real Principals, not fixture-vs-fabricated.
- `TestIntegration_ResolveApproval_SelfApprovalDenied` — **strengthened**: previously passed by coincidence. Its fabricated Approval's `RequestingPrincipalID` is set to `fixtures.ApproverPrincipal().PrincipalID`; before this fix, `ResolveApproval` *always* used that same fixture as decider, so the self-collision was structural. Without `DecidingPrincipal` now explicitly set to the same value, the request would trip `ErrNonHumanDecider` (zero-value `Principal.Kind`) instead of `ErrSelfApproval` — a *different* failure mode that happens to map to the same `Outcome: Denied`, silently testing the wrong thing. Fixed by setting `DecidingPrincipal` explicitly and adding an assertion on the specific reason string (`self_approval_prohibited`), so this test can't silently start testing non-human-decider-denial instead of self-approval-denial again.
- Every other pre-existing test that calls `CreateWorkflow`/`StartWorkflow`/`CancelWorkflow`/`ResolveApproval` (~30 call sites across `integration_test.go`, `knowledge_integration_test.go`, `objective_integration_test.go`, `idempotency_race_integration_test.go`, `approval_invariants_integration_test.go`, `pipeline_test.go`, `runtime_test.go`) now passes an explicit `RequestingPrincipalID`/`DecidingPrincipal` — `app.Fixtures.TriggerPrincipal().PrincipalID` / `app.Fixtures.ApproverPrincipal()` where the test isn't specifically about attribution, a fresh `uuid.New()` where fake-repo tests don't need a real one — rather than silently defaulting to a zero-value `uuid.Nil`/empty `principal.Principal{}`, which would have made every approval-resolution test fail on `ErrNonHumanDecider`.
