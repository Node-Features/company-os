# Fixed: Runtime Dispatch Resilience (Panic Recovery + Concurrency Bound)

Status: IMPLEMENTED (2026-08-24) — implemented and verified against the real database, including repeated full-suite runs. **Not yet committed to git** as of this writing — check `git status` before assuming this is landed on a branch.

This is the implementation record for [`gap-runtime-resilience.md`](gap-runtime-resilience.md) (P1). Read that doc first for the original problem statement and plan; this document is the "what actually shipped, what it proves, what's still open" record, in the same shape as [`fixed-execution-lifecycle-hardening.md`](fixed-execution-lifecycle-hardening.md) (which this work builds on directly — both gaps touch `Runtime.Sweep`'s dispatch loop, and the gap doc itself named implementing them together as the natural sequencing).

## What was implemented

`Runtime.Sweep` ([runtime.go](../../apps/companyd/internal/runtime/runtime.go)) previously spawned one bare goroutine per claimed intent (`go func(c execution.ClaimedExecution) { defer r.wg.Done(); r.execute(ctx, c.Attempt, c.Intent) }(c)`), with no panic recovery and no bound on how many could run at once. Replaced with a single new primitive, `Runtime.dispatchBounded(fn func())`, and `Sweep` now calls it once per claim instead of spawning the goroutine inline:

1. **Panic recovery.** `dispatchBounded`'s goroutine wraps `fn()` in `defer func() { if rec := recover(); rec != nil { log.Printf(...) } }()`. A panic inside `execute()` — a malformed provider response, an unhandled edge case — is now logged and contained to that one dispatch; every other concurrently-dispatching intent, and the daemon process itself, keeps running.

2. **Bounded concurrency.** A new `Runtime.MaxConcurrentDispatch int` field sizes a semaphore (`chan struct{}`), lazily created (race-safely, via the same `sync.Once` that already builds `workCtx`) with capacity `MaxConcurrentDispatch`, or `defaultMaxConcurrentDispatch` (10) when left unset — so a zero-value `Runtime` fails safe (bounded) rather than fail open (unbounded). `dispatchBounded` acquires a slot (`r.sem <- struct{}{}`) **inside** the goroutine, after `r.wg.Add(1)`, so a dispatch still queued behind a saturated semaphore correctly counts as in-flight work `Daemon.Shutdown`'s drain must wait for — not work that was silently dropped or, worse, not counted at all. `cmd/companyd/main.go` now sets `MaxConcurrentDispatch: 10` explicitly alongside `PollInterval`/`LeaseDuration`, the same "field on `Runtime`, set by the caller" convention those two already use (no env-var plumbing exists for either today; this doesn't add a new configuration mechanism, just reuses the existing one).

3. **No separate overlapping-sweep guard.** The gap doc left this as an open design choice ("consider whether overlapping `Sweep` calls need coordination... or whether the concurrency bound makes it unnecessary"). Resolved: no. Claiming is already exclusive per row (`FOR UPDATE SKIP LOCKED`, [`fixed-execution-lifecycle-hardening.md`](fixed-execution-lifecycle-hardening.md)), so two overlapping sweeps can never dispatch the same intent twice; and now that dispatch itself is bounded, overlapping sweeps just mean more goroutines queued behind the same semaphore — no unbounded resource use results, so no additional guard earns its complexity.

4. **No new "panicked" state.** The gap doc's plan step 1 asked for the panic to leave the attempt "in a state the reclaim mechanism can pick up." No extra bookkeeping was needed to achieve that: by the time `execute()` can panic, its `ExecutionAttempt` is already either `CLAIMED` (if the panic happens before `RecordDispatched`) or `DISPATCHED` (after) — both are already within `ReclaimExpiredLeases`' WHERE clause ([`fixed-execution-lifecycle-hardening.md`](fixed-execution-lifecycle-hardening.md)'s state-transition diagram). A panicked dispatch is therefore recovered by the *same* lease-expiry mechanism that recovers a crashed process — not a second, parallel recovery path.

## Tests added

`internal/runtime/runtime_unit_test.go` gained four tests, all pure-Go/no-database (same rationale as this file's pre-existing `TestSweep_DatabaseFailure_DoesNotPanic`: reliably injecting a panic or precise concurrency contention through a real Postgres-backed `execute()` call would require faking `*application.Application` — a concrete struct with no interface seam — so these test `dispatchBounded` directly, the level at which the panic-recovery/concurrency-bound mechanics actually live, independent of what `fn` happens to be):

- `TestDispatchBounded_PanicRecovered_OtherDispatchesStillComplete` — the gap doc's "before" baseline (today's actual behavior is a crash) turned "after" assertion: one panicking dispatch alongside five normal ones; the test process doesn't crash, and all five non-panicking dispatches still complete.
- `TestDispatchBounded_ConcurrencyNeverExceedsBound` — the gap doc's load-test requirement: 20 dispatches queued against a bound of 3; proves via a signal channel (not a fixed `time.Sleep` — see the test's own comment) that at most 3 ever run concurrently. Deliberately deterministic: since none of the first 3 releases its semaphore slot until the test closes a shared `release` channel, draining exactly 3 "started" signals is itself proof the bound was reached, with no race against wall-clock timing.
- `TestDispatchBounded_DefaultBoundAppliesWhenUnset` — proves a zero-value `MaxConcurrentDispatch` yields `defaultMaxConcurrentDispatch` (10), not an unbounded channel — fails safe, not open.
- (pre-existing, unchanged) `TestSweep_DatabaseFailure_DoesNotPanic` and `TestReclaimAbandoned_DatabaseFailure_DoesNotBlockClaiming` still pass unmodified — `Sweep`'s failure-handling shape didn't change, only how it dispatches successful claims.

The full pre-existing `internal/runtime` suite (13 `TestIntegration_Runtime_*` real-database tests from the lease-reclaim work, covering normal execution, duplicate delivery, worker crash, lease expiration, concurrent claim, retry, provider failure, stale version, cancellation, recovery after restart, and `StopWork`) was re-run against the real database after this change and passed unmodified — `dispatchBounded` is a drop-in replacement for the inline goroutine, not a behavior change to `execute()` itself.

## Race detector: still unavailable in this environment, reconfirmed

[`fixed-execution-lifecycle-hardening.md`](fixed-execution-lifecycle-hardening.md) already noted `go test -race` was unavailable (cgo/gcc toolchain gap). This session re-checked that assumption from scratch, since a working `gcc.exe` (MSYS2, Rev5) is now present and `go build -race ./internal/runtime/...` (pure compile, no link) succeeds — suggesting the earlier note might have been stale. It wasn't: `go test -race` still fails, isolated with `-x` to the **link step** specifically — `cgo.exe` invoked to build GOROOT's own `runtime/cgo` bootstrap package (`C:\Program Files\Go\src\runtime\cgo\cgo.go`) exits status 2 with zero compiler diagnostics of any kind, reproduced identically after a full `go clean -cache`, scoped to a single trivial test, and with no other concurrent Go process running. Zero-diagnostic-output-exit-2 from `cgo.exe` (rather than a real gcc compiler error, which normally prints before failing) points at the toolchain plumbing itself (likely a Go/MinGW-gcc ABI or antivirus-process-spawn issue on this Windows host), not at anything in this repository's code. Not pursued further — same call the prior session made, still correct: this is an environment limitation to fix separately, not a blocker for this work.

**Substituted per the same precedent**: `internal/runtime`'s tests were run three consecutive full times (real database, `go test ./internal/runtime/... -count=3 -timeout=40m` — the default 10-minute per-binary timeout isn't enough headroom for three real-database passes back to back, confirmed by one run hitting exactly that wall with a goroutine dump mid an active DB call, not a deadlock, then passing clean once given real time) plus the whole-module `go test ./...` once, specifically to catch nondeterminism the race detector would otherwise catch — the same standard [`fixed-execution-lifecycle-hardening.md`](fixed-execution-lifecycle-hardening.md) and [`fixed-test-suite-nondeterminism.md`](fixed-test-suite-nondeterminism.md) already established.
